# Overview

This lab demonstrates **Out-of-Band (OAST) SQL Injection**, where the application provides no visible output, no SQL errors, and no measurable timing differences.

Instead of relying on the application's response, the attacker forces the database server to make an external request to **Burp Collaborator**. Receiving this request confirms that the injected SQL statement was successfully executed.

---

# Lab Objective

Exploit a Blind SQL Injection vulnerability by triggering an out-of-band interaction with Burp Collaborator.

---

# Understanding the Vulnerability

Some applications provide absolutely no feedback to the attacker.

When this happens, traditional Blind SQL Injection techniques become ineffective.

Out-of-Band SQL Injection solves this problem by making the database communicate with an external server controlled by the tester.

If Burp Collaborator receives a DNS or HTTP request, it confirms successful SQL execution.

---

# Attack Methodology

1. Capture the vulnerable request.
2. Send the request to Burp Repeater.
3. Insert a Burp Collaborator payload.
4. Trigger an external request from the database.
5. Confirm SQL Injection through Burp Collaborator.

---

# Solution Walkthrough

## Step 1 – Capture the Request

Open the lab in **Burp Browser**.

Locate the request containing the `TrackingId` cookie and send it to **Burp Repeater**.

---

## Step 2 – Inject the SQL Payload

Replace the `TrackingId` cookie with an Out-of-Band SQL Injection payload.

Locate the placeholder:

```text
BURP-COLLABORATOR-SUBDOMAIN
```

Right-click and choose:

**Insert Collaborator Payload**

Burp automatically replaces it with your unique Collaborator domain.

---

## Step 3 – Send the Request

Send the modified request.

The database attempts to resolve the external XML entity, causing it to communicate with Burp Collaborator.

---

## Step 4 – Verify the Interaction

Open:

**Burp → Collaborator**

Click:

**Poll now**

**Observation**

Burp Collaborator receives one or more **DNS** and/or **HTTP** interactions.

This confirms that:

* The SQL Injection payload executed successfully.
* The database initiated an external request.
* The application is vulnerable to Out-of-Band SQL Injection.

# Payload Analysis

### `EXTRACTVALUE()`

Processes XML data within Oracle.

### `xmltype()`

Creates an XML document from the supplied payload.

### `<!ENTITY>`

Defines an external XML entity.

### Burp Collaborator

Provides a unique external endpoint used to detect DNS and HTTP interactions generated by the target application.

---

# Why the Attack Works

Although the application provides no visible response, the database still executes injected SQL statements.

By forcing the database to make an external request to Burp Collaborator, attackers obtain confirmation that their payload executed successfully without relying on application output.

---

# Detection Tips

Security testers can identify this vulnerability by:

* Using Burp Collaborator during Blind SQL Injection testing.
* Monitoring DNS and HTTP interactions.
* Testing Oracle XML functions capable of making external requests.
* Comparing Collaborator interactions after different payloads.

---

# Common Mistakes

* Forgetting to insert a Collaborator payload.
* Polling Collaborator before sending the request.
* Assuming no webpage changes mean the payload failed.
* Using payloads designed for a different database platform.

---

# Real-World Scenario

Highly secured enterprise applications often suppress query results, database errors, and timing differences.

Out-of-Band SQL Injection allows testers to verify SQL Injection by observing external network interactions, making it one of the most effective techniques for assessing hardened applications.

---

# Mitigation

Developers should:

* Use parameterized queries.
* Restrict outbound network access from database servers.
* Disable unnecessary XML features.
* Monitor outbound DNS and HTTP traffic.
* Regularly perform SQL Injection testing.

---

# Key Takeaways

* Out-of-Band SQL Injection does not rely on application responses.
* Burp Collaborator provides an external communication channel.
* DNS and HTTP interactions confirm successful SQL execution.
* Restricting outbound connectivity reduces the impact of OAST attacks.
